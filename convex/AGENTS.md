# Ownership

# Local Contracts

- Read `convex/_generated/ai/guidelines.md` before editing handwritten Convex code.
- Treat `convex/_generated/` as generated output unless a documented Convex workflow explicitly requires regeneration artifacts to be committed.
- Keep handwritten Convex code compatible with the generated API and data model surface in this subtree.
- Tenancy/auth/audit foundation lives in `schema.ts`, `validators.ts`, `auth.ts`, `http.ts`, `users.ts`, `tenancy.ts`, `portal.ts`, `admin.ts`, `auth.config.ts`, `convex.config.ts`, and `lib/`.
- Portfolio data: a client is one tenant + its organization (profile fields: industry, clientType, relationshipStatus, accountManagerName, clientSince). `clients.ts` (list/get/create/update), `properties.ts` and `leases.ts` (list/get/create/update/archive; leases also add/removeClause) own the `properties`, `leases`, `leaseClauses` tables. Archive is a soft delete (`archivedAt`); lease dates are ISO `YYYY-MM-DD` strings and "expiring"/"renewal window" states are derived from `endDate`, not stored.
- Sourcing: `sourcing.ts` owns tenant-scoped `sourcingBriefs` and `propertyCandidates` (scores embedded on candidates). Staff writers create immutable rental briefs with idempotent request IDs; staff in the tenant read history/results; client users cannot. `runResearch` calls Mastra using Convex deployment env `MASTRA_SOURCING_URL` (full reachable `/sourcing/research` URL) and `MASTRA_SOURCING_SERVICE_TOKEN` (same secret on Mastra). Claim/completion are internal and terminal results are immutable; a six-minute expiry resolves stuck searches and rejects late results. `lib/sourcing.ts` is the shared validated contract and type/provenance filtering utility. Candidates carry optional `imageUrl`, the photo from the listing page itself (absent on older rows). No automated publication or insertion into portfolio properties.
- Shared helpers: `lib/auth.ts` (`getTenantAccess`/`requireTenantAccess`, `requireTenantWriter` = staff and not `read_only_staff`, `requireStaff`, `listStaffTenants`, `actorTypeFor`), `lib/provisioning.ts` (`seedRoles`, `provisionClientTenant`, `createClientInvitation`), `lib/portfolio.ts` (validation, live-lease rules). New tenant-scoped features must use these instead of ad hoc membership queries.
- Target deployment: production `focused-malamute-656` (team `mcmarsh-fif-gmail-com`, project `megatrend`), URL `https://focused-malamute-656.convex.cloud`. No dev deployment is configured.
- Production property research uses `MASTRA_SOURCING_URL=https://mega.cyphersoftai.com/api/sourcing/research`; the portal forwards to the registered Web Research Agent in its local Mastra runtime. The same server-only service token must be configured in Convex and Dokploy.
- Deploy with `CONVEX_DEPLOYMENT=prod:focused-malamute-656 npx convex deploy` (or `CONVEX_DEPLOY_KEY` in CI). `CONVEX_DEPLOYMENT` is intentionally not stored in `.env.local`.
- `VITE_CONVEX_URL` lives in `insightful-property-hub/.env.local` (Vite env dir) and root `.env.local`; both are gitignored.
- Authentication is Convex Auth (`@convex-dev/auth`) with the email + password provider only, configured in `auth.ts`; `http.ts` must keep `auth.addHttpRoutes(http)`. `auth.config.ts` trusts `CONVEX_SITE_URL` with `applicationID: "convex"`.
- Deployment env required for auth: `SITE_URL`, `JWT_PRIVATE_KEY`, `JWKS` (set by `npx @convex-dev/auth --prod`), plus `PLATFORM_ADMIN_EMAILS` (comma-separated).
- Sign-up is invite-only: `auth.ts` `createOrUpdateUser` rejects new accounts unless the email is in `PLATFORM_ADMIN_EMAILS` or has a pending, unexpired `membershipInvitations` row; pending invitations are accepted on account creation and again on `users.syncCurrentUser`.
- The `users` table is the Convex Auth table (keep its fields and `email`/`phone` indexes) extended with `lastSeenAt`. Resolve the current user with `getAuthUserId` via `lib/auth.ts` helpers; never add a parallel identity table.
- Access model: platform admins (email in `PLATFORM_ADMIN_EMAILS`) reach every tenant; everyone else needs an active membership. Staff = platform admin or any active staff membership; only staff edit portfolio records; client users read their own tenant. A user may hold several membership rows per tenant, so look memberships up with `findActiveMembership`, never `.unique()`.
- Creating clients (`clients.create`, `tenancy.provisionTenant`) and `admin.seedRoleCatalog` require `requirePlatformAdmin`. `admin.seedRoleCatalogInternal` seeds roles from the CLI (`npx convex run admin:seedRoleCatalogInternal`); `provisionClientTenant` also seeds idempotently.
- `portal.getPortalContext` returns `{status: ok|forbidden|not_found}` instead of throwing; the portal shell relies on it. Re-inviting a revoked user reactivates their existing membership row. Users cannot revoke themselves; client admins cannot revoke staff.
- Throw `ConvexError` for user-facing messages (plain `Error` text is hidden as "Server Error" in production).
- Documents: originals live in Convex file storage. `documents.ts` (generateUploadUrl, create, replace, list, get, getFileUrl, reprocess, requestDeletion) owns `documents`; `processing.ts` owns the pipeline and `extractedFields`. Upload validation (25 MB, Docling-supported types, property in tenant) returns `{documentId: null, error}` instead of throwing, so the rejected file's storage delete is not rolled back. Clients request deletion; staff deletes are soft (`deletedAt`, file kept for retention). Replacing hides the old record via `replacedByDocumentId`. Read-only roles (`read_only_staff`, `executive_viewer`) cannot upload (`requireTenantUploader`).
- Processing: `documents.create`/`reprocess` schedule `processing.start`, which runs Windmill flow `f/docling/process_document_for_app` with the file's signed URL and polls `jobs_u/get` every 10 s (max ~15 min) — no inbound webhook. Status: uploaded → queued_for_ocr → ocr_complete → extraction_complete | review_required (low confidence vs `tenantSettings.publishConfidenceThreshold`, missing required fields, or no fields) | processing_failed; `approved` is reserved for staff review. Results from a superseded job id are ignored. New extracted fields carry `attemptId`; re-runs preserve earlier field decisions and select current fields by ownership instead of rewriting history.
- Processing env (Convex deployment): `WINDMILL_BASE_URL`, `WINDMILL_WORKSPACE`, `WINDMILL_PROCESSING_TOKEN` (Windmill token `convex-document-processing`, scoped to run that flow + `jobs:read`). Without them uploads are stored but not processed. `npx convex run processing:checkConnection '{"fileUrl":..., "filename":..., "viaConvexStorage":true}'` tests the pipeline without DB writes; it leaves `selftest/` objects in MinIO `parsedinjson`/`okfdata`, so delete them afterwards.
- Review (`review.ts`): staff approve / correct-and-approve / reject each extracted field; `approveHighConfidence` only touches `detected` fields, never `low_confidence_review`; `completeReview` sets the document `approved` only when no field is pending and closes the automatic review action. `applyToLease` copies only APPROVED lease fields to a lease (update or create) plus area/landlord to the property, stamping `sourceDocumentId`/`approvedAt`/`approvedBy` (shown to clients as human-approved). `queue` is the urgency-ranked review inbox.
- Insights (`insights.ts`): draft → under_review → published | rejected; published → withdrawn. Clients only read `published`; publishing requires evidence (a document or lease) and notifies client users; published insights must be withdrawn before editing.
- Actions (`actions.ts`): statuses open, in_progress, waiting_on_client, waiting_on_cyphersoft, waiting_on_landlord, completed, cancelled ("overdue" is derived from `dueDate`). `visibleToClient: false` tasks and `internal` comments never reach clients; client-created actions are always client-visible `client_request`s; clients may only set completed/open; a client reply moves waiting_on_client → waiting_on_cyphersoft. Automatic actions use `lib/autoActions.ts` with an `autoKey` (`document:<id>:missing` client-visible, `document:<id>:review` internal) so re-processing never duplicates them.
- Notifications (`notifications.ts`, `lib/notifications.ts`): in-app only; `staffRecipients` = tenant staff members + platform admins, `clientRecipients` = active client members; the actor is never notified. Links are in-app paths (`/documents/<id>`, `/tasks`, `/portal/<slug>/...`). Email delivery is not implemented.
- Invoices & anomalies (`lib/invoices.ts`, `invoices.ts`): `review.completeReview` on an invoice/utility_statement records an `invoices` row from APPROVED fields (supplier + amount required; one row per document, re-reviews update it). Baseline = mean of up to 6 earlier invoices with the same tenant, property, `supplierKey` and kind (needs ≥ 3). Increases ≥ 15/30/50 % → medium/high/critical `cost_spike`; same invoice number, or same date and amount → `possible_duplicate`. Each anomaly gets an internal `anomaly:<id>` action, a `draftedBy: "system"` draft insight and a staff notification. Clients see their invoices but only anomalies with `sharedWithClient`; resolving/dismissing closes the action.
- Voice usage (`voice.ts`): public `consume({kind: "transcribe" | "assistant"})` is called by the portal server as the signed-in user before every OpenRouter/Mastra voice call. One `voiceUsage` row per user per UTC day stores counts only (never audio or transcripts); limits come from deployment env `VOICE_RATE_LIMIT_PER_MINUTE` (default 10) and `VOICE_DAILY_CAP` (default 200) and throw user-facing `ConvexError`s.
- Overview queries: `dashboard.staffOverview` / `dashboard.clientActivity` (activity text from `auditEvents` via `lib/activity.ts`; clients only see client-safe event types), `reports.portfolio`, `search.global` (search indexes `organizations.search_name`, `properties.search_name`, `documents.search_filename`, `documents.search_text` on `textPreview`; staff only). Keep these bounded with `.take()`.
- Automations (`lib/automations.ts`, `automations.ts`, `crons.ts`): definitions are code (`AUTOMATIONS`, `RENEWAL_STEPS`); the `automations` table only stores enabled/run counters (missing row = enabled). Crons run `automations.runScheduled` daily at 05:00 UTC (renewal cadence) and 05:15 UTC (overdue reminders). Renewal cadence fires each T-180/150/120/90/30/7 step once per lease and end date (tracked in `renewalMilestones`); when catching up it fires only the latest reached step and records older ones as `skipped`. Steps create actions with `source: "automation"` (T-180 and T-7 client-visible), notifications, and (T-180) a `system` draft insight. Overdue reminders notify clients about overdue `waiting_on_client` actions at most every 6 days (`lastReminderAt`). `invoice_anomaly_check` is event-driven: when paused, invoices are still recorded but not flagged. Every execution writes an `automationRuns` row (`scheduled` | `manual` | `dry_run` | `event`); dry runs never write actions/notifications. Only platform admins toggle or "run now"; any staff can simulate.

# Work Guidance

- Phase 10: `signingPortfolio.ts` owns append-only company-scoped `portfolioParties`/`portfolioUnits`, explicit draft `portfolioContext`, reviewed immutable `signingApplications`, internal ZAR `signingPayments`, independent `signingLeaseDecisions`, and permanent `signingEffects` receipts. New context is hashed only when present; legacy completed agreements get a separately reviewed mapping. Both owner and renter require explicit participant representation. Never infer a renter from a workspace tenant or signing authority from membership.
- Applying a completed agreement requires admin + recent MFA and the exact preview hash; stale lease rows or changed replay payloads fail. Create/renew inserts `pending`; amend stores prior values and preserves operational status. Renewals link predecessor/successor, and separate activation retires the predecessor. Pending leases carry no live rent and trigger no renewal cadence. Activation rejects overlapping live leases for the same explicitly linked unit. Ordinary lease update/archive/clause edits and OCR application cannot alter signing-managed leases; use a signed amendment/review. Legacy unmanaged leases retain their existing behavior.
- Signed, active, paid and occupation-authorised states are independent. Activation and occupation each require admin + MFA, the current reviewed application ID and a reason/reference; decisions retain that application ID and reject stale tabs after an amendment. Payment evidence cannot set either state. Payment requests are internal records, with no payment gateway or money movement. Completion publication atomically creates one internal review task/staff notice through `completionEffects`; permanent receipts prevent replays from recreating closed tasks. Reviewed applications atomically create the selected payment/move-in effects; renewal reminders reuse the existing cadence after activation and respect `signingRenewalReminders`.
- `signingReports.ts` reports a company/date cohort by agreement creation time, current outcomes across indexed pages, and median issuance-to-completion for completed transactions only. Provider acceptance/delivery/verification/signing stay distinct. Report limits fail explicitly, with no partial total.
- `signingExports.ts` captures an admin/MFA-approved transactional company snapshot and redacts invitation/session/email transport credentials. `signingExports` owns one reserved Windmill job per request; `claim` is atomic, unknown submissions are reconciled and never resubmitted. Full handovers include available validated sources, annexures, attachments and completed artifacts/evidence; missing required bytes/hash/version failures block publication. Explicit bounds: 700 KB metadata snapshot, 2,000 rows per collection, 400 artifacts and 100 archive volumes. No truncation, deletion or legal-hold changes. Downloads require fresh admin MFA and append audit evidence. Runbooks document export permissions and live acceptance.

- Signing foundation: `signing.ts`, `lib/signing.ts`, `lib/signingAudit.ts` and the `signing*` tables own administrator-only draft writes, company-staff reads, immutable draft/participant revisions, request replay protection and agreement event chains. Clients (including users who are staff in another company) cannot browse signing records. Do not reuse general document/lease read access for signing evidence.
- `signing.readiness` reports `canIssue` and `releaseBlockers` from `lib/signingRelease.ts`. Policy and release references never prove legal validity, service health or production readiness. Approval requires the current worker-validated `signingBundles` pointer, matching draft/file revision and unexpired retained artifact. Issuance, reminders, reissue and next-stage activation pass the two-key release gate (`assertRelease`/`releaseBlockers`): deployment env `SIGNING_RELEASE_MODE` (`pilot`/`live`, otherwise off) AND an unsuspended `signingReleases` record (admin+MFA, evidence references) AND complete policy/category AND configured services; pilot mode allowlists every recipient address. Neither key alone opens sending; never add another bypass. No public bundle registration endpoint exists.
- `signingFiles.ts` owns administrator/MFA upload tickets, exact quarantine versions, file order/removal and company-staff verified prepared downloads; never accept a browser-selected source key, version, URL or resource. `signingPreparations.ts` reserves remote job IDs before submission and validates job ownership, snapshot/manifest hashes, source identities, geometry and retained artifact receipts. Ambiguous jobs retain ownership; reconcile rather than resubmit. Metadata/file edits invalidate bundles and are blocked during unresolved preparation. Confirmed failure permits a new attempt; stale/voided or duplicate completion cannot publish.
- Signing PDFs remain separate from OCR document storage. Only `f/signing/prepare_bundle`, using dedicated private storage/scanner resources and `WINDMILL_SIGNING_DOCUMENTS_TOKEN`, prepares them. New optional fields preserve compatibility with Phase 1 records; legacy bundles without Phase 2 evidence cannot satisfy approval.
- `lib/signingFields.ts` and `signingFields.ts` own bounded field definitions, explicit crop/rotation transforms and immutable `signingLayouts`. Coordinates use `crop-top-left-unrotated-v1`; size minima are physical points including user units. Save checks draft/bundle/layout versions, signer ownership and locked/typed constraints (400 fields, 200 KB canonical evidence). Signature/initials cannot be administrator-locked; dates are server-owned. Every signer needs a required signature before approval.
- `requestApproval` requires the exact reviewed preparation hash binding fields, page geometry, parties/stages, PDF/manifest versions, policy copy and consent. Its optional wire argument exists for compatibility, not a bypass. `decideApproval` atomically stores `signingFrozenPreparations` and decision/audit bindings on approval only. Frozen snapshot, layout, decision identity/reason/time and approval event must remain consistent; `approvalCurrent` fails closed on missing/altered evidence. Policy changes or returning to draft invalidate current approval; old immutable evidence stays retained.
- Metadata/PDF changes clear current layout/frozen pointers. Field-only edits retain the PDF but append a new layout and clear current approval. No existing layout or frozen snapshot is updated in place. Later issuance must use the verified frozen snapshot and still enforce `canIssue`, not infer authorization from a status label or a layout hash alone.
- Phase 4: `signingInvitations.ts` owns administrator/MFA invitation controls and redacted company-staff delivery reads. `signingTransactions` binds frozen evidence, participants and active stage. Reissue rotates the version/nonce/hash, invalidating old challenges and sessions; reminders preserve credentials and use permanent actor/request deduplication. `createIssuedTransaction` is unregistered; callers must enforce current approval, operator authority and the release gate. Issue/reissue/remind/revoke require a platform administrator with tenant writer access and recent MFA (`requireSigningWriter`). Reminders go only to outstanding current-stage signers/approvers without an unresolved delivery, at most once per 24 hours.
- `signingAccess.ts` is the server-token-authenticated POST `/signing/access` boundary. `signingAccessState.ts` commits rate limits, OTP attempts, revocations and sessions. Never pass raw link/code/session credentials to internal functions or expose them through normal queries. Only the first-party portal proxy receives successful credentials. GET and link exchange do not send mail, consent, view a document or sign. Authentication means mailbox verification, not certified identity.
- `lib/signingAccessCrypto.ts` uses Web Crypto HKDF/HMAC/AES-GCM and versioned server keys. Invitation hashes and session/challenge hashes are purpose-separated. OTP hashes are keyed. Encrypted short-lived email outbox payloads are the sole transport exception to hash-only credential storage; they are deleted on acceptance/rejection/expiry. Retain required historical key IDs; key removal fails closed. Configuration/resource contracts live in the frontend signing prerequisites runbook.
- `signingDeliveries.ts` reserves Windmill job IDs before POST and verifies path/input digest on reconciliation. Unknown outcomes never automatically send again, including beyond Resend's 24-hour idempotency period. Pending delivery checks use the invitation/status index, so older unresolved jobs cannot disappear behind a history page. Expired/revoked/stale queued messages are suppressed. `signingWebhooks.ts` uses official Svix raw-body verification; `signingDeliveryEvents.ts` permanently deduplicates event ID/body hash and binds provider ID, delivery tag, sender and recipient HMAC. Delivery facts and lookup observations are separate; opens/clicks never become authenticated views.
- Signing events support optional external `actorKind: provider|signer` and participant keys without a fabricated staff actor. Include those fields in the hashed envelope only when present, preserving existing staff event hashes. All external evidence events append through the same audit/checkpoint helper.
- Draft revisions are not frozen issued PDF versions. Editing creates immutable snapshots with bounded participants (20) and notes (10,000 characters); expected revision rejects stale writes. Create/update request IDs are scoped to company + authenticated actor and cannot be reused with different payloads. Issued cancellation must not use `voidDraft` because it must also revoke access.
- Signing events and checkpoint outbox rows append atomically with changes. `verifyAudit` is DB-only (`consistent_unanchored`, explicit 1,000-event limit). `signingCheckpoints.verify` reads independent Windmill/S3 storage directly, checks retained/versioned anchors against events/revisions and distinguishes a protected prefix from a fully anchored head. Worker failures remain pending/failed; no fabricated receipt, silent downgrade, or unbounded retry. Keep PII out of checkpoint/shared activity payloads.
- Signing writes require recent session-bound MFA through `lib/signingSecurity.ts`. Node actions in `signingMfa.ts` use OTPAuth and AES-256-GCM; `signingMfaState.ts` commits rate limits, replay counters, one-use recovery consumption and five-minute grants atomically. Validate live Convex Auth session ownership/expiry; do not add an MFA bypass. Configured keyrings stay in typed Convex env, encrypted secrets in private tables, and setup/recovery secrets only in their single setup response.
- `signingMfaState` exposes only status publicly; credential queries, verification claims/results and enrollment storage are internal. Failed verifications return errors rather than throw after mutation so counters commit. Five failures lock for 15 minutes; unconfirmed reenrollment preserves limits. Credential replacement invalidates all old-version grants.
- Phase 5 signer portal: `signerPortal.ts` (internal only) is reached through the service-token `/signing/access` operations `portal`, `document`, `consent`, `save_draft`, `adopt_mark`, `submit`, `decline`, `request_correction`; `signingAccess.ts` hashes the session credential first. Only an `active` session (valid invitation, current stage) writes; `completed`/`paused`/`closed` modes are read-only. Consent, drafts and marks bind one invitation version. Drafts are optimistic-revision saves and never signatures. `signerMarks.sanitize` (Node) rebuilds PNG marks from critical chunks with CRC/inflate checks; store only its output.
- `signingSubmissions` rows are immutable evidence (sign/approve/decline/correction_request) keyed by a unique request key; repeats return the existing receipt. Submission re-checks session, version, stage, expiry, consent hash, presented preparation/PDF hashes, reviewed draft revision and every field; locked values, read-only names and signing dates come from the frozen snapshot/server. Stage completion activates waiting invitations via `activateStage` (request-keyed deliveries); the last stage sets transaction `signed` and agreement `finalising`. Decline sets agreement `declined`; correction pauses the transaction only. Never add a public status setter.
- Phase 6 finalisation: `lib/signingFinalisation.ts` (`startFinalisation`, result schema, error codes) and `signingFinalisation.ts` own `signingFinalisations` (one job and artifact prefix per attempt) and `signingCompletions`. Claim only from `finalising` with transaction `signed` and one intact accepted submission per signer/approver; the canonical evidence manifest and its digest are fixed at claim. Reserve the job ID before POST; only the agreement's current attempt/job may publish, and only after strict result validation (keys, hashes, page count, timestamp, PAdES-B-LT facts). Failure stays `finalising`; transient codes auto-retry three times; others need admin+MFA `retry`. Never resubmit an ambiguous job (`reconcile` polls). Uses `WINDMILL_SIGNING_FINALISE_TOKEN`, never the preparation token.
- Read-only participant access (`readOnlyInvitation`/`accessibleInvitation`): completed participants (and paused transactions) can re-verify and read receipts; after completion access lasts at least 14 days. Only completed signers/approvers (not decliners or viewers) receive the sealed copy (`final_document`). Writes still require an active invitation.
- Phase 7: `signingExceptions.ts` owns void (approved/issued; revokes unfinished invitations and sessions), bounded deadline extension (≤30 days), resume after correction, replacement (new draft linked by `replacesAgreementId`/`replacedByAgreementId`; open agreements become `superseded`), held-stage resumption, scheduled expiry (`expireDue`, cron) and legal holds. All writes require admin+MFA and a reason, append signing events and never delete or edit submissions/evidence.
- `signingOperations.ts`: `scan` (cron) raises PII-free `signingAlerts` for stuck/ambiguous jobs, failed/overdue finalisation, unresolved/rejected/stuck deliveries, checkpoint problems and near deadlines, notifying platform admins once per opening and resolving scan-owned kinds when no longer observed; `alerts` is platform-admin only. `purgeTransient` (cron) deletes unfinished drafts, unused marks and OTP challenges of terminal agreements after policy `transientRetentionDays` (default 90) unless a legal hold is active; it never deletes submissions, consents, events, sessions, delivery facts or finalisation records. Alert messages carry codes only.
- Phase 8 templates: `lib/signingTemplates.ts` owns the closed document schema (`normalizeDoc`: Tiptap JSON limited to headings, paragraphs, bold/italic/underline, lists, tables, rules, page breaks, merge fields, conditional sections, clause references, schedule table), the merge-field catalog, integer-cent schedule maths (`computeSchedule`, half-up rounding, annual compounding escalation, per-period VAT) and the deterministic escaping HTML renderer (`TEMPLATE_RENDERER`; bump it whenever output could change). `signingTemplates.ts` owns company template/clause libraries: approved versions are immutable, edits create new versions, approval needs admin+MFA, a legal reference and a different approver unless policy allows self-approval, and pins the approved version/hash of every referenced clause. Starters are placeholder structures, never approved legal text.
- Generation (`signingTemplates.generate`) only for drafts with idle preparation and unchanged revision/file revision: it stores a snapshot (facts with provenance, entered values, conditions, schedule input, annexure selections, generation date), input/HTML hashes and renderer version, then `f/signing/render_template` writes the PDF once into quarantine. `completeGeneration` attaches it as the primary file only if nothing changed; otherwise the generation is superseded. Generated PDFs follow the normal scan/preparation path. `reproduce` re-renders from the stored snapshot and pinned versions; never read live portfolio data when reproducing.
- Phase 9 fields: `radio`/`dropdown` (2–20 unique options; approved fixed values must be an option), one-level `showIf` conditions (same signer, unconditional checkbox/choice source, valid value) and `attachment` fields with a declared `purpose`. Hidden fields are neither required nor recorded (`fieldVisible`); conditional signatures never satisfy the required-signature rule. Adopted marks and clean attachment SHA-256 values are the only draft references (`ReferenceKind`).
- Phase 9 participants: optional `witnessFor` (a signer attesting another non-witness signer in the same or later stage), E.164 `phone`, `notifyVia` (email default; SMS/WhatsApp need a phone; WhatsApp needs `whatsappOptInReference`) and draft `signatureMethod: "advanced"`. Absent optional values are omitted so earlier content hashes are unchanged; use `partyContent` when rebuilding hashed participant content. `methodBlockers` blocks approval for witnessing without policy `witnessingReference`, any SMS/WhatsApp channel and advanced signatures: no SMS/WhatsApp/accredited provider is accepted, so these stay gated (do not add sending paths without a recorded provider/legal acceptance).
- In-person sessions (`signingInPerson.start`, admin+MFA): staff record an identity check (document type and only its last 2–4 characters) and receive a 15-minute single-use kiosk credential stored as a hash in `signingInPersonChecks` (a new check revokes unused ones). `/signing/access` `kiosk_exchange` opens the normal challenge; the OTP still goes to the participant's own mailbox, so staff cannot act for them. Sessions record `authMethod: "in_person_email_otp"`; submission evidence includes the check (type, ending, staff ID, time); the audit event omits the ending.
- Supporting documents (`signingAttachments`): portal operations `attachment_form`/`attachment_complete` reserve an upload for the participant's own attachment field (PDF/JPEG/PNG, ≤10 MB, ≤40 per invitation), then the worker type-checks, ClamAV-scans and retains it. Scanner/storage outages stay `pending` (retryable); content failures become `rejected`. Staff `signingAttachments.list` is metadata only; `open` needs admin+MFA and a ≥10-character reason, audited before the 60-second link. Never OCR or pass attachments to assistants.
- Approval requests bind exact revision/content/PDF/manifest hashes, immutable artifact key/storage version, and policy revision/hash. Their authority/content binding hash and request-event sequence also bind them to the append-only event stream. Self-approval defaults off. Policy changes derive stale approval state, decisions reject changed bindings, and returning to draft creates a new revision and removes the current approval pointer. Never approve mutable source references or edit issued terms in place.

- File previews are independent of OCR/review: `documentPreviews.ts` owns a file-only authorized view, read-authorized conversion requests, and the `documentPreviews` table. `documents.previewId` selects the current preview; cache identity is original storage ID + renderer version. Public callers never choose URLs, job IDs, output storage IDs or converter settings. Existing replaced originals retain the same access as `documents.getFileUrl`; deleted documents are unavailable.
- Preview conversion uses the separate `WINDMILL_PREVIEW_TOKEN` (run `f/docling/render_document_preview` + jobs read), with the existing Windmill base URL/workspace. Atomically claim before scheduling/submission; reserve the job ID and polling before the network call. Five-minute expiry requires explicit retry; late results cannot publish and their generated files are deleted. Poll late jobs for up to one hour to collect outputs. Do not modify extraction attempts, review decisions, or publication status when viewing files.
- `documentPreviews.checkConnection` is an internal operator smoke test taking `{filename, inputBase64}` for a synthetic Office/TIFF fixture. It exercises the production token, storage and Windmill renderer without application records, returning job/PDF metadata and deleting source/output files. Never pass customer content or invoke it from public UI. A timed-out test's job ID requires operator inspection for a late output.

- Document attempts (`processing.ts`, `processingAttempts`): `claim` atomically sets `documents.activeAttemptId` before submission. Reserve a Windmill UUID (`job_id` query parameter), attach it and schedule polling atomically. Only the current nonterminal attempt can attach jobs or update progress/results/failures; deleted/replaced documents reject updates. Repeated completion is a no-op.
- Stage outcomes: `documents.processingStages` stores parse/knowledge/extract status, timestamps, bounded sanitized errors, retry classification, artifact references, and reuse provenance. Windmill continues to the summary after stage failures; explicit parse/extraction failure without usable fields becomes `processing_failed`. Partial parsing/truncation with usable fields requires acknowledged review. Knowledge failure disables document search but does not invalidate extraction or staff publication; show that failure independently.
- Targeted recovery (`processing.retryStage`): staff writers claim atomically against the displayed extraction attempt; callers never supply artifact keys. Parse retries reread the original and rerun dependent work. Extraction retries validate and reuse the saved parsed JSON and preserve the knowledge outcome, replacing only current extraction ownership and decisions. Knowledge retries use `activeRecoveryAttemptId` with `sourceAttemptId` tied to the unchanged extraction pointer; they preserve fields, publication, source-coverage acknowledgement, and processing/review timestamps. Both pointers block overlapping processing and are checked on every callback. Retain historical attempts and reused artifact ownership.
- Retry policy: transport/rate-limit failures are retryable; invalid input requires correction/replacement. Staff can retry configuration failures after restoring settings. Client responses use static guidance rather than raw stage errors or artifact paths; only staff receive technical stage details. The public recovery and reconciliation mutations require tenant staff-writer access.
- Waiting timeout is not remote cancellation. Keep owned attempts running with `timedOut`, block duplicate starts, and reconcile at 60-second intervals for up to four hours after the initial waiting budget. Legacy jobs use `processingRemoteUnresolved` for the same hold. A confirmed remote completion/failure resolves ownership; stale results from terminal or superseded attempts remain ignored. `processing.reconcile` lets staff check held jobs again; restore configuration first if unavailable. Unresolved jobs require operator investigation and are never blindly released.
- Attempt recovery: a claim not submitted within 60 seconds becomes `abandoned` and can be retried. Ambiguous submissions become `submission_unknown`; `recoverSubmission` checks the reserved job's path and attempt input for up to 90 checks and never blindly resubmits. Unresolved submissions remain quarantined; operators can invoke `processing:recoverSubmission` with `{documentId, attemptId, check: 1}` after investigating/restoring job access. Do not release a quarantine merely because a lookup returned 404.
- Processing contract v1 stores bounded stage/artifact/provenance metadata on the attempt. Truncation, partial/unknown parsing or extraction, missing sections, malformed output, and new attempts receiving legacy output set `processingIncomplete` and force review. Existing jobs without an active attempt can finish through exact matching legacy job IDs; legacy callbacks cannot update owned attempts or reattach a retried record.
- Incomplete coverage requires `review.acknowledgeIncomplete` (staff writer, current attempt, reason) before `completeReview` or `applyToLease`. Keep the warning and audited acknowledgement after approval; a new claim clears the previous acknowledgement. Applying values while processing is active is forbidden.
- Current fields: use `lib/documentFields.ts` in document details, review, record application, invoices, and reporting. Select the document/attempt index before reading rows; only extraction-complete, review-required, or approved documents expose fields. Deleted/replaced documents and fields from obsolete attempts cannot be reviewed. AI draft facts inherit this selection through `documents.get`.
- Legacy fields: when no tagged current-attempt fields exist, use the document/current-job index and accept only untagged fields matching that exact job. This also supports Phase 1 records with an attempt pointer and untagged fields. Keep optional `extractedFields.attemptId` and both indexes during rollout. No backfill is needed to deploy these additive changes. Before removing the fallback, backfill matching current untagged fields in bounded batches; legacy documents without an attempt need a validated completed attempt and pointer first. Preserve historical decisions and never infer current ownership from creation order or field state.
- Field bounds: processing currently accepts up to 100 fields; complete current-field reads support up to 1,000 indexed rows and fail explicitly above that size, preventing partial bulk decisions or record application. `documents.listFields` offers pages of up to 100 rows, with the current attempt/job required on each request; restart pagination when processing changes. Individual decisions check current ownership without loading the full catalogue. Increase the full-review bound or implement batched completion before supporting extraction catalogues above 1,000 rows.
